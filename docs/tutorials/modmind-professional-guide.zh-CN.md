# ModMind 专业模式完整使用手册

> 适用范围：ModMind 1.3.11 专业模式。本文面向 Minecraft Mod 开发者、整合包作者、迁移维护者和需要完整交付流程的技术用户。界面可能随版本更新调整，但项目边界和工作流原则保持不变。

如果你只想快速完成第一个作品，请先阅读[新手教程](./modmind-first-mod.zh-CN.md)。本文按功能组织，可以从目录中直接进入需要的章节，不要求按顺序操作。

## 1. 能力范围

专业模式覆盖以下项目类型：

| 项目类型 | 支持范围 | 主要成品 |
| --- | --- | --- |
| Java Mod | Fabric、Quilt、Forge、NeoForge | Mod JAR |
| Java 整合包 | Modrinth 整合包、第三方 Mod、自制模块 | `.mrpack`、服务端包 |
| 国际基岩版 Add-on | 行为包、资源包、脚本 | `.mcaddon` |
| 网易版工程 | 网易手游、网易 PC Mod SDK 工程 | 开发者工作台归档 |
| 现有工程 | 文件夹、ZIP、MRPack、残缺源码、API 文档 | 接管后的 ModMind 项目 |

专业模式提供：

- AI 工作台、只读灵感台和外部 Coding Agent；
- Monaco 文件编辑器、VS Code 工作区入口和 Blockbench；
- 图像生成、处理、编辑和项目资源导入；
- 依赖、联动源码、Mappings 和资源数据工具；
- Gradle Wrapper 构建、客户端、服务端、GameTest 和 HeadlessMC 验证；
- Git、项目快照、版本迁移和任务恢复；
- Modrinth、CurseForge、GitHub Releases 发布；
- 整合包下载、锁定、内容、任务书、服务端和迁移工具。

## 2. 环境与项目边界

### 2.1 外部环境

ModMind 可以按需管理 Java、Minecraft 测试实例和下载缓存，但专业用户通常还应准备：

- Git，用于提交、分支、远程同步和 Pull Request；
- VS Code，用于使用外部 IDE 工作区；
- 可用的 Codex 或 Claude Code，本机 Agent 模式需要；
- 对应平台账号和 Token，仅在发布或远程构建时需要；
- 正版 Minecraft 账号，HeadlessMC 登录测试需要。

ModMind 不安装独立的系统 Gradle。Java 项目始终调用项目中固定的 Wrapper：

```powershell
.\gradlew.bat build
```

在 macOS 或 Linux 上对应：

```bash
./gradlew build
```

不要为了绕过 Wrapper 错误而改用全局 Gradle。Wrapper 版本、插件版本和 Loader 工具链属于项目可复现构建的一部分。

### 2.2 项目内文件

新项目使用以下两个核心位置：

```text
<project>/modmind.project.json
<project>/.modmind/
```

- `modmind.project.json` 保存项目名称、命名空间、平台、Minecraft 版本和 Loader 等元数据；
- `.modmind` 保存快照、任务恢复点、迁移记录和项目级工具数据；
- 源码、资源、Gradle 文件、整合包覆盖内容仍位于标准项目目录；
- 旧版 `.modtool` 项目在接管时会执行兼容迁移，不应继续作为新项目格式使用。

`.modmind` 不是普通构建缓存。删除它可能同时丢失快照、恢复点和迁移依据。清理项目前应先确认其中是否存在仍需保留的记录。

### 2.3 应用级数据与凭证

以下数据不应写入项目或 Git：

- Agent API Key；
- 图像服务 API Key；
- Modrinth、CurseForge、GitHub Token；
- Gitee Personal Access Token；
- 本机账号会话和应用下载缓存。

ModMind 对界面中保存的凭证使用系统加密存储。不要把 Token 写入提示词、源码、`gradle.properties`、截图或诊断说明中。

## 3. 专业模式与导航

右上角的 **专业模式** 开关控制完整开发界面。开启后，Java Mod 项目通常显示：

| 分组 | 功能 |
| --- | --- |
| 创作 | 工作台、灵感台、资源、模型、代码、前置与联动、游戏测试、构建与导出 |
| 项目 | 发布、版本、Mappings、设置 |

整合包项目会按“整合包、内容、运行、项目”展开更多专用工具。侧边栏项目和分组可以拖动排序，设置页可恢复默认顺序。

专业模式不会改变项目格式，也不会建立另一份工程。快速制作与专业模式读取的是同一项目，区别只在于显示的控制范围和技术细节。

## 4. 创建、打开与接管项目

### 4.1 新建项目

**新建项目** 用于生成全新工程。创建前应确认：

- 项目类型是自制 Mod 还是整合包；
- Java、国际基岩版或网易版平台；
- Loader 与 Minecraft 版本；
- 命名空间和项目名称是否适合长期使用。

项目建立后再改显示名称相对简单，但更换命名空间、Loader 或 Minecraft 大版本通常需要迁移，不应当作普通重命名处理。

### 4.2 打开已有项目

**打开已有项目** 只用于已经由 ModMind 管理、包含有效项目描述文件的目录。它不会重新识别任意源码目录。

### 4.3 接管现有项目

**接管现有项目** 支持文件夹、ZIP 和 MRPack。ModMind 会先分析来源，再显示识别结果：

- 完整工程：保留原结构并建立 ModMind 项目元数据；
- 残缺源码：创建可管理项目并导入已有文件；
- 整合包实例：识别 Loader、版本、模组和覆盖内容；
- API 文档：作为可检索的参考内容接入项目。

接管前应检查自动推断的项目名称、命名空间、Minecraft 版本和 Loader。完整工程的 Loader 通常由现有构建文件决定，不应在导入时强行改写。

接管后建议立即完成三项基线操作：

1. 创建一个“导入基线”快照；
2. 查看 Git 状态并确认没有意外生成文件；
3. 在未进行功能修改前执行一次构建或平台归档。

## 5. AI、Agent 与灵感台

### 5.1 后端选择

专业工作台可以选择：

- **消耗额度：** 使用 ModMind 提供的托管能力；
- **Codex：** 使用本机 Codex CLI 和配置；
- **Claude Code：** 使用本机登录配置，或配置 ModMind 中转服务。

所有后端通过 ModMind 项目工具桥访问受管能力。切换后端不会自动把一个服务的凭证复制给另一个服务。

### 5.2 配置外部 Agent

打开 **设置 → AI 与 Agent**，选择 Agent 后可以配置：

- 命令路径，留空时从 `PATH` 查找；
- 本机登录或中转服务模式；
- Base URL；
- API Key；
- 模型 ID，可扫描服务模型或手动填写；
- 思考强度。

保存配置前，ModMind 会保留原配置备份。使用本机模式时，通常应沿用 CLI 自己的账号和配置，不必重复填写服务地址。

高思考强度适合迁移、跨模块重构和复杂崩溃定位；简单资源修改使用中等强度通常更经济。模型名称存在不代表模型一定支持所需工具调用，应以一次真实项目任务验证。

### 5.3 工作台任务

工作台任务可以直接修改代码和资源。输入区支持文字和附件；执行后会显示：

- 任务开始与恢复的上下文；
- Agent 的工具结果、重试、警告和代码修改；
- 当前待办计划；
- 本次修改的文件；
- 构建和自动验收结果。

适合专业任务的提示词应写清楚约束和验收，而不是指定大量未经验证的实现细节：

```text
目标：为现有 Fabric 1.21.1 项目增加可配置的区域伤害机制。

约束：
- 保持现有 public API 和资源 ID 不变；
- 不升级 Loader、Mappings 或 Gradle 插件；
- 服务端负责伤害判定，客户端只处理表现；
- 配置使用现有 AutoConfig 依赖，不新增配置库；
- 修改前检查项目现有事件注册和测试模式。

验收：
- Gradle build 通过；
- 专用服务器启动不加载客户端类；
- 增加覆盖默认值、禁用状态和伤害间隔的测试；
- 最后列出修改文件、兼容性影响和需要进游戏验证的项目。
```

附件适合提供崩溃报告、界面参考、协议说明和上游 API 文档。不要上传与任务无关的私密目录或凭证文件。

### 5.4 暂停、恢复与回滚

执行中的任务可以 **暂停任务**。ModMind 会保留任务检查点和项目恢复点；下次打开项目时可以继续执行。

AI 写入前会保存安全快照。出现以下情况时应优先恢复，而不是继续叠加修复：

- Agent 改变了任务范围之外的 Loader 或构建配置；
- 资源 ID、包名或公共 API 被大面积重命名；
- 构建虽然通过，但关键行为被删除；
- 连续修复开始反复修改同一组文件。

恢复快照前，ModMind 会先备份当前现场。仍然建议在重要功能完成后创建带语义名称的手动快照和 Git 提交。

### 5.5 灵感台

**灵感台** 用于只读分析和创意讨论，不执行编程。它适合：

- 分析项目结构和技术债；
- 比较 API 或玩法方案；
- 阅读导入的源码和文档；
- 讨论性能、兼容性和实现成本。

满意的结果可以通过 **交给工作台** 送到编码区，确认后再执行。不要把灵感台回答误认为已经落地的修改。

## 6. 代码、资源与模型工具

### 6.1 代码编辑器

**代码** 页面提供项目文件树和 Monaco 编辑器，支持：

- 新建文件和目录；
- 重命名、删除和保存文件；
- 在文件管理器中显示文件；
- 使用常见代码和配置文件的语法高亮；
- 在 VS Code 中打开完整项目。

未保存文件会显示状态标记。执行构建、迁移、恢复快照或 AI 任务前，应先保存编辑器内容。二进制文件不会在文本编辑器中打开，应使用对应专用工具或文件管理器。

> **图片 06：代码编辑器**  
> 建议截图：打开一个 Java 源文件，展示文件树、编辑区、未保存标记和 VS Code 入口。

### 6.2 图像工坊

图像工坊包含三类能力：

- **工作流：** 组合提示词、参考图、图像生成、图像处理和输出节点；
- **处理：** PerfectPixel、去背景、撤销和编辑器入口；
- **编辑：** 新建画布或导入图片后进行像素与常规编辑。

输出可以放大预览、另存为或加入项目。使用参考图时可以选择本地图片，也可以直接读取项目图片资源。

专业项目应在加入资源前确认：

- 目标路径和命名空间；
- PNG 尺寸、透明通道和插值方式；
- 是否需要 16×16、32×32 等像素风格；
- 生成内容的授权与发布平台要求。

### 6.3 Blockbench

**模型** 页面嵌入 Blockbench，并提供项目桥接。可以打开和保存 Blockbench 项目、切换模型/纹理等编辑模式，并把模型工作流留在 ModMind 项目上下文中。

保存前检查模型格式与目标平台是否匹配：Java 方块/物品模型、模组实体模型和 Bedrock 实体模型不是同一种格式。模型文件、纹理和动画控制器的资源路径必须保持一致。

### 6.4 生产中心的内容工具

Java Mod 的 **发布 → 内容** 可以生成或维护：

- 语言键；
- 有序和无序配方；
- 物品、方块标签；
- 方块掉落表；
- 进度；
- 任意 Data JSON 和 Asset JSON；
- 音频及声音事件。

生成后运行 **验证资源**。工具可以发现格式和引用错误，但复杂数据包行为仍应进入游戏或通过 GameTest 验证。

## 7. Mappings 与依赖联动

### 7.1 Minecraft Mappings

**Mappings** 页面按当前 Minecraft 版本查询 Mojang、Yarn、Intermediary 等命名空间。可以：

- 搜索类名或包名；
- 查看类声明；
- 对照各命名空间类名；
- 筛选字段、构造器和方法；
- 打开 Loader 文档或 mappings.dev 原始页面。

Mappings 查询结果会本地缓存。实现跨版本修改时，先确认目标版本的实际签名，不要凭另一版本的示例猜测方法名。

### 7.2 前置与联动

**前置与联动** 管理直接目标、自动前置和 API 来源。来源可以是：

- Modrinth、CurseForge 或 MC 百科搜索结果；
- 本地 JAR；
- 另一个本地项目；
- 源码归档或源码目录。

每个目标需要明确关系：

- **必须安装：** 成品运行必需；
- **可选联动：** 缺失时项目仍能运行；
- **仅测试：** 只进入测试环境，不进入发布要求。

专业模式会显示 JAR/源码匹配状态、类数量和可用包范围。导入本地 JAR 时应核对平台匹配结果与文件指纹，私人或定制 Mod 需要手工确认。

### 7.3 生产依赖中心

**发布 → 依赖** 侧重构建依赖和锁定：

- 搜索与当前 Loader、Minecraft 版本兼容的 Modrinth 项目；
- 添加 `group:artifact:version` Maven 坐标；
- 选择 `implementation`、`modImplementation`、`compileOnly` 或 `runtimeOnly`；
- 添加 HTTPS Maven 仓库；
- 更新、移除并审计依赖锁文件。

“前置与联动”和“生产依赖”不能混为一谈：前者描述成品关系和可用 API，后者决定构建解析与锁定。一个联动目标可能同时需要正确的 Gradle 依赖和发布依赖声明。

## 8. 构建、预检与游戏测试

### 8.1 构建与导出

**构建与导出** 执行真实项目构建和 Preflight。页面保留：

- 当前构建状态；
- 通过/失败统计；
- Gradle 和预检输出；
- 任务时间线；
- 构建成功后的导出入口；
- 构建失败后的 **AI 修复**。

Java 项目生成 Mod JAR；基岩项目校验双 Pack 并生成 `.mcaddon`；网易项目校验 Mod SDK 结构并生成工作台归档。

构建成功不等于发布就绪。至少还要验证：运行侧隔离、资源加载、玩法行为和发布元数据。

### 8.2 Minecraft 测试实例

Java 项目的 **游戏测试** 页面可以：

- 准备托管 Java、Minecraft 和 Loader；
- 设置离线测试用户名和最大内存；
- 构建并同步当前项目 JAR；
- 保留用户额外加入的依赖 Mod；
- 启动或停止测试游戏；
- 查看运行日志和崩溃摘要；
- 对运行期崩溃执行 AI 修复并重启。

离线身份只适合本地普通启动。需要正版认证的 HeadlessMC 功能必须完成官方账号配置，不应被当作认证绕过手段。

### 8.3 无头冒烟、服务端与 GameTest

专业验证应覆盖不同风险面：

| 验证项 | 主要发现的问题 |
| --- | --- |
| Build | 编译、资源处理、依赖解析 |
| Client | 客户端入口、渲染、资源加载、Mixin |
| Dedicated Server | 客户端类误加载、服务端注册、网络侧问题 |
| Loader GameTest | 可自动断言的玩法和数据行为 |
| Headless smoke | 启动、登录环境、进服或基础运行链路 |
| Manual playtest | 手感、表现、数值、交互和多人体验 |

**发布 → 测试矩阵** 可以选择构建、客户端、专用服务器和 Loader GameTest，并生成 CI 工作流。CI 生成后仍需审查 Java 版本、缓存、密钥和 Runner 环境。

## 9. Git、快照与任务恢复

### 9.1 三者的职责

| 机制 | 用途 | 不应替代 |
| --- | --- | --- |
| Git | 可审查历史、分支、协作、远程备份 | 临时任务恢复 |
| ModMind 快照 | 本机全项目快速恢复 | 团队代码审查和远程备份 |
| Agent 恢复点 | 继续中断的 AI 任务 | 长期版本管理 |

### 9.2 Git 工作流

**版本** 页面内置 Git 工作流，支持：

- 初始化 `main` 分支并生成适合 Mod 项目的 `.gitignore`；
- 查看工作区变更和逐文件 Diff；
- 提交全部变更；
- 配置本地提交身份；
- 创建并切换分支；
- 添加、移除远程仓库；
- Fetch、仅快进 Pull 和 Push；
- Merge、Rebase 和打开 GitHub PR 页面。

推荐在 Agent 任务前保持工作区干净，在任务后按“查看 Diff → 构建/测试 → 提交”的顺序处理。不要在未审查时把自动生成的大范围修改直接推送到主分支。

### 9.3 快照

快照保存到项目 `.modmind` 目录，可创建、恢复和删除。恢复前会自动备份当前现场，恢复失败时也有回滚保护。

适合创建快照的节点包括：

- 接管现有项目后；
- 大版本迁移前；
- Loader 切换前；
- 大规模资源重组前；
- 复杂 Agent 任务前；
- 发布候选版本通过测试后。

## 10. Java Mod 版本迁移

Java Mod 的 **版本 → 迁移目标** 支持选择 Fabric、Quilt、Forge 或 NeoForge 及目标 Minecraft 版本。流程为：

1. 选择目标 Loader 和版本；
2. 运行预检；
3. 阅读稳定/实验支持级别、警告和阻塞项；
4. 在无阻塞项时生成迁移项目；
5. 在新目录中完成 API、资源和行为迁移；
6. 独立构建并测试目标工程。

迁移生成到新目录，不应覆盖原工程。工具可以迁移结构和部分配置，但不能保证跨 Loader API、Mixin 目标、注册方式和第三方依赖自动等价。

基岩与网易工程不执行 Java Loader 自动迁移。升级最低引擎或 Mod SDK 前应创建快照，并按目标平台 API 逐项验证。

## 11. 发布 Java Mod

**发布** 页面中的生产中心包含“依赖、内容、测试矩阵、发布”四个标签。进入发布前，确保依赖审计、资源验证和测试矩阵已经完成。

### 11.1 发布配置

发布中心可以设置：

- 版本和显示名称；
- 摘要和更新日志；
- Release、Beta 或 Alpha 通道；
- Patch、Minor 或 Major 自动递增；
- Modrinth 项目 ID 与 Token；
- CurseForge 项目 ID 与 Token；
- GitHub `owner/repository` 与 Token；
- 本次实际发布的平台组合。

保存后 Token 使用系统加密存储。留空已保存的 Token 字段表示保持原值，不代表删除。

### 11.2 发布门禁

发布顺序必须是：

1. 保存配置；
2. 执行发布预检；
3. 修复所有失败项；
4. 选择目标平台；
5. 阅读不可自动撤销的确认信息；
6. 明确确认后发布；
7. 在各平台检查文件、依赖、版本和更新日志。

发布是外部不可自动撤销操作。不要使用测试项目 ID、错误通道或未确认的 Token 权限进行正式发布。

## 12. 国际基岩版与网易工程

专业模式对非 Java 工程保留工作台、资源、模型、代码、构建与导出、版本和设置，但不会显示 Java 专属的 Mappings、Gradle 依赖和 Minecraft Java 测试实例。

### 12.1 国际基岩版

构建时重点校验：

- 行为包与资源包 Manifest；
- UUID 和依赖关系；
- 脚本入口与模块声明；
- 资源路径和平台版本；
- `.mcaddon` 归档结构。

构建后必须在目标基岩版客户端中导入并验证。Java 版的注册、Mixin、Mappings 和 Gradle 经验不能直接套用到 Add-on。

### 12.2 网易版

网易工程以 Mod SDK 结构和官方开发者工作台为最终运行边界。ModMind 可以检查工程并生成工作台归档，但平台审核、能力权限和真机行为仍以网易平台为准。

迁移或发布前应明确手游/PC 目标，不要混用运行目标和 SDK 版本。

## 13. 整合包专业工具

整合包项目拥有独立的完整导航。以下各节可以按需使用。

### 13.1 整合包创作

工作台允许 Agent 读取整合包并修改任务、配置、资源或脚本。提示词应明确：

- 目标玩家人数和游玩时长；
- 核心玩法阶段；
- 客户端、服务端和双方内容边界；
- 允许增加或移除的 Mod；
- 是否允许改动配置、KubeJS、任务书和世界；
- 验收所需的客户端与服务端场景。

### 13.2 文件清单

**文件清单** 汇总 MRPack 远程来源和本地覆盖内容。它用于审查最终分发边界，不只是文件浏览器。

对每项内容应确认：来源、目标路径、客户端/服务端作用域、远程或覆盖交付方式，以及是否允许重新分发。

### 13.3 模组列表

**模组列表** 分为第三方模组和自制模组。支持：

- 导入本地 Mod；
- 搜索、排序和批量移除；
- 审计锁定清单；
- 创建独立自制 Mod 模块；
- 为模块设置客户端、服务端或双方端类型；
- 单独打开和构建自制模块。

锁定清单记录文件大小和 SHA-256。文件被手工替换后应重新审计，不能只看文件名或版本字符串。

### 13.4 模组下载

**模组下载** 可以在 Modrinth、CurseForge 和 MC 百科之间选择，并按当前 Minecraft 版本和 Loader 筛选文件。下载前检查：

- 文件版本与 Loader；
- 客户端/服务端运行侧；
- 必需前置；
- 项目许可证和整合包分发权限；
- 平台匹配是否精确。

MC 百科来源可能要求验证码。

> 建议截图：第三方/自制模组列表和多平台下载详情。  
> 建议标注：`锁定清单`、`端类型`、`来源`、`兼容版本`。

### 13.5 配置与默认项

管理 `config`、`defaultconfigs` 和 `serverconfig`。新增内容时选择正确作用域：

- `common`：客户端与服务端都需要；
- `client`：仅客户端分发；
- `server`：仅服务端分发。

`defaultconfigs` 是新世界默认值，不等同于现有世界已经生成的 `serverconfig`。发布更新时应说明哪些设置只对新世界生效。

### 13.6 脚本与 KubeJS

管理 KubeJS 客户端/服务端脚本和其他启动脚本。重点检查：

- 脚本运行侧；
- 对 Mod ID 和物品 ID 的引用；
- 配方删除与新增顺序；
- 重载和完整重启的行为差异；
- 服务端是否错误引用客户端对象。

### 13.7 数据包、资源包、光影包与界面资源

- **数据包：** 管理普通数据包、OpenLoader 和 Paxi 目标，可创建 `pack.mcmeta` 和函数入口；
- **资源包：** 导入客户端视觉 ZIP；
- **光影包：** 管理客户端光影 ZIP；
- **界面资源：** 管理 FancyMenu、默认选项和相关资源包。

下载或导入时应确认目标路径、作用域和是否解压。资源包和光影包通常保持 ZIP，世界存档则需要识别并解压包含 `level.dat` 的目录。

### 13.8 存档与世界

**存档与世界** 用于分发初始世界或可导入存档。导入前应清理：

- 玩家身份和位置数据；
- 不需要的日志、崩溃报告和缓存；
- 服务器地址、Token 或管理脚本中的秘密；
- 大体积临时区块和备份文件。

### 13.9 玩家预设

**玩家预设** 读取 `options.txt`，支持搜索动作、录入键盘/鼠标按键、清除绑定、筛选冲突和保存预设。

默认情况下不应保存冲突。确需保留时开启“允许保存冲突”，并在整合包说明中告知玩家。可以随时打开原文处理未被可视化界面覆盖的字段。

### 13.10 服务端配置与文件工作台

- **服务端配置：** 管理 `serverconfig` 和服务端默认项，并查看已同步到服务端包的实际 Mod 清单；
- **文件工作台：** 管理无法归入标准分类的 MRPack 覆盖文件和 `global_packs` 等自定义位置。

使用文件工作台时必须更谨慎，因为自定义位置不会天然具备正确的客户端/服务端语义。

### 13.11 FTB 任务书

FTB 任务书编辑器支持：

- JSON5 和 SNBT 任务书；
- 章节创建与排序；
- 可视化任务节点和前置连线；
- 标题、副标题、图标、形状和描述；
- 手动确认、提交物品和到达位置条件；
- 物品、经验和命令奖励；
- 撤销、重做、复制和高级 JSON 字段。

存在结构错误时不能保存。命令奖励属于高风险内容，应在服务端测试环境中检查权限、选择器和重复领取行为。

### 13.12 Patchouli 指南书

Patchouli 编辑器按分类和条目组织引导内容，可以写入完整基础书籍。发布前应验证：

- Patchouli 是否属于必需依赖；
- 书籍 ID、分类 ID 和条目 ID 是否稳定；
- 图标物品在对应阶段已经可用；
- 多语言内容与任务阶段一致。

### 13.13 依赖与优化

**依赖与优化** 包含：

- 根据目标 Mod 名称生成兼容方案；
- 在展示未解决项后安装方案；
- 对已记录 JAR 执行大小和 SHA-256 审计；
- 应用只包含当前版本兼容候选的性能优化档。

优化档不是性能结论。应用后仍需比较启动时间、内存、TPS、客户端帧时间和兼容性，且应保留应用前快照。

### 13.14 本机服务端

**本机服务端** 支持准备或导出服务端包、启动/停止/重启、实时控制台、发送命令、本机联机验证和服务端场景。

服务端场景通过发送命令并要求日志出现指定证据来判断通过。它适合验证启动、模组加载、命令和基础联机，不等于完成长时间稳定性测试。

### 13.15 整合包游戏测试

游戏测试会同步整合包内容而不是只同步一个项目 JAR。每次改变 Mod 列表、配置、脚本或资源后都应重新同步。

至少测试：全新实例、已有存档升级、客户端单机、本机服务端、多人连接、缺失可选客户端 Mod 和服务端无客户端专属 Mod 的情况。

### 13.16 整合包版本迁移

整合包迁移提供目标 Loader/版本扫描，并把结果分为兼容、可替换、缺失、未知和源码移植。作者需要逐项决定：

- 使用兼容候选；
- 手工导入目标 JAR；
- 创建源码/自制兼容模块；
- 暂缓并生成不完整报告；
- 从目标包移除。

自制模块和魔改内容需要分别决定是否迁移源码、复制配置/脚本/任务/资源/世界或排除。优先使用 **备份并迁移**；直接迁移没有同等的撤销依据。

迁移完成后必须重新执行锁定审计、客户端测试、服务端测试和任务线检查。迁移历史中的可撤销记录会在撤销前再次保存当前现场。

### 13.17 版本与导出

整合包交付页面可以设置版本、显示名称、摘要、更新日志和自动递增方式，并提供：

- **AI 草拟摘要**；
- **导出服务端包**；
- **导出 `.mrpack`**。

版本只应在成功导出后递增。发布 `.mrpack` 前检查远程依赖是否仍可下载、本地覆盖文件是否完整、客户端/服务端作用域是否正确以及第三方内容是否允许分发。

## 14. 设置、远程构建与诊断

### 14.1 图像服务

可以配置 Base URL、默认图片模型和 API Key。未填写自有 Key 时可能使用 ModMind 托管额度。外部 Agent 可以通过图像 Skill 调用同一能力，生成操作会记录额度。

### 14.2 构建设置

构建设置明确显示项目 Wrapper 行为。遇到 Wrapper 下载或校验错误时，应检查项目配置、网络和缓存，不要假设 ModMind 会回退到全局 Gradle。

### 14.3 诊断日志

**导出诊断日志** 会收集应用事件、下载重试、Minecraft、构建、服务端日志和页面快照，并对已保存的 API Key 和 Token 做排除或脱敏。

提交问题时同时提供：

- ModMind 版本与操作系统；
- 项目类型、Minecraft 版本和 Loader；
- 最短复现步骤；
- 预期与实际结果；
- 最近一次成功状态；
- 诊断归档和必要截图。

发送前仍应自行检查归档，避免项目源码、路径或第三方日志中存在不希望分享的业务信息。

### 14.4 关闭、通知和外观

可以配置深色模式、任务完成通知，以及关闭窗口时询问、最小化到托盘或直接退出。长时间 Agent、下载或构建任务运行时，应避免误选直接退出。

### 14.5 Gitee Go 远程构建

远程构建支持配置：

- Gitee 仓库地址；
- 构建分支；
- 具有仓库读写权限的 Personal Access Token。

流程为：创建并启用 Gitee Go 仓库 → 校验连接 → 保存配置 → **推送并开始远程构建** → 打开 Gitee 流水线查看状态和制品。

ModMind 会生成 `.gitee-ci.yml`、提交并推送。远程平台是否有免费额度、流水线是否启用以及构建节点环境仍由 Gitee 账号和平台策略决定。Token 只应授予所需仓库权限。

## 15. 常见问题定位表

| 现象 | 首先检查 | 下一步 |
| --- | --- | --- |
| 无法同步modminds账号 | 账号key是否正常 | 前往官网充值或手动签发key |
| Agent 无法启动 | 命令路径、CLI 安装、账号状态 | 在设置中重新检测或打开 Agent 文档 |
| Agent 能回答但不修改 | 是否在灵感台、任务是否被识别为咨询 | 将结果交给工作台并明确修改与验收 |
| 构建依赖解析失败 | Wrapper、仓库 HTTPS、坐标和网络 | 查看 Gradle 原始错误，审计依赖锁 |
| 构建通过但客户端崩溃 | 运行日志、Mixin、资源、客户端入口 | 使用游戏测试和运行期 AI 修复 |
| 专用服务器崩溃 | 客户端类误加载、环境依赖 | 运行测试矩阵的 Dedicated Server 项 |
| 资源显示缺失 | 命名空间、大小写、模型与纹理路径 | 运行资源验证并检查构建产物 |
| 修改未进入游戏 | 未保存、未重新构建、未同步 | 停止实例，保存后构建并同步 |
| 整合包文件被替换 | SHA-256 或大小与锁定不符 | 审计锁定并重新确认来源 |
| 整合包迁移卡住 | 仍有未取舍 Mod 或阻塞内容 | 选择替代、手工 JAR、移植、暂缓或移除 |
| 发布按钮不可用 | 未保存配置、预检未通过、未选平台 | 按发布门禁顺序重新检查 |
| 远程构建未触发 | 仓库、分支、Token、Gitee Go 状态 | 打开流水线页面检查平台配置 |
| 无法继续中断任务 | 恢复点损坏或项目路径变化 | 查看诊断日志，恢复安全快照后重做任务 |

## 16. 专业交付检查清单

### 项目与代码

- [ ] 项目元数据中的平台、Loader 和 Minecraft 版本正确；
- [ ] 工作区没有未经审查的 AI 修改；
- [ ] 源码、资源 ID 和公共 API 改动已审查；
- [ ] Git Diff 清晰，提交信息可追溯；
- [ ] 发布候选状态已创建快照和 Git 标签或提交。

### 依赖与安全

- [ ] 所有 Maven 仓库使用 HTTPS；
- [ ] 必需、可选和仅测试依赖区分正确；
- [ ] 依赖和整合包锁定审计通过；
- [ ] 项目中没有 API Key、Token、账号数据或私密服务器信息；
- [ ] 第三方资源和 Mod 的许可证允许当前分发方式。

### 构建与验证

- [ ] 使用项目 Gradle Wrapper 构建通过；
- [ ] Preflight 和资源验证通过；
- [ ] 客户端启动与基础玩法通过；
- [ ] 专用服务器启动通过；
- [ ] GameTest 或对应自动测试通过；
- [ ] 手工检查数值、表现、交互和多人行为；
- [ ] 迁移项目在目标版本独立验证。

### 发布与交付

- [ ] 版本、通道、显示名称、摘要和更新日志正确；
- [ ] 发布平台项目 ID 和依赖声明正确；
- [ ] 正式 Token 使用最小权限并由系统加密保存；
- [ ] 发布预检通过；
- [ ] 已核对导出的 JAR、`.mcaddon`、工作台归档或 `.mrpack`；
- [ ] 外部平台发布后已再次检查文件和版本页面。

专业模式的核心不是把所有工具都用一遍，而是让每次修改都有输入约束、执行证据、可审查差异、可复现构建、分层测试和可恢复版本。只要这六个环节完整，AI、编辑器、迁移和发布工具就能进入同一套可靠的工程流程。
