# ModMind 世界级 Minecraft IDE 与整合包创作平台开发计划

状态：规划基线。本文是基于当前代码、当前产品入口以及已确认需求形成的总计划，不代表本次立即实施全部功能。

本文覆盖以下并行目标：

- 升级专业模式和必要的小白模式体验。
- 将 Monaco 从基础单文件编辑器升级为 Minecraft 项目级代码编辑器。
- 让数据包、配置、KubeJS、服务端配置等内容在原页面内直接编辑，不再被强制送入全局通用文件工作台。
- 让 ModMind 在日常 Java/Kotlin Minecraft 模组开发中逐步替代 IntelliJ IDEA 和 VS Code。
- 建立整合包架构 Skill、版本化半成品蓝图和质量验证闭环，降低生成成本并提高成品质量。
- 为缺少目标版本文件的模组提供受控的 JAR 分析、反编译和迁移辅助。
- 在现有 MCP 之外建立完整的 ModMind 插件生态接口。

## 1. 已确认的产品决策

### 1.1 用户模式

小白模式原本计划保持不动，后续已确认：如果界面或流程确实影响体验，可以调整小白模式；但它仍然保持低门槛，不暴露完整专业工具链。小白模式的核心闭环是：

```text
描述需求 -> AI 制作 -> 自动检查 -> 启动测试 -> AI 修复 -> 导出
```

专业模式面向整合包作者、模组开发者、迁移开发者和高级维护者，提供完整的编辑、构建、测试、迁移、Git、发布和插件能力。

### 1.2 编辑器交互

- 当前内容页需要上下文内编辑。
- 数据包、配置、KubeJS、服务端配置、界面资源、玩家预设等文本内容统一采用同一种返回和保存逻辑。
- 上下文编辑器一次专注一个文件，不做多标签页。
- 页面顶部保留来源、内容类别、文件路径和返回入口。
- 复杂场景可以选择“在完整文件工作台中打开”，但不能把它作为默认路径。
- 完整文件工作台可以保留单文件专注模式；不应依赖多标签才能完成工作。

### 1.3 IDE 目标

目标不只是“整合包作者不需要 IDEA”，还包括 Java/Kotlin 自制模组、附属模组、兼容模组和版本迁移开发。

最终目标是：用户在 Minecraft 开发场景中不需要依赖 IDEA 或 VS Code 完成日常编辑、构建、测试、调试、迁移和发布。外部 IDE 入口在达到稳定覆盖率前保留为应急出口，不作为主要工作流。

### 1.4 整合包与 AI

- 整合包蓝图不限制题材，首批可以覆盖科技、冒险、魔法、原版增强、多人服务器等方向。
- AI 应通过任务决策 Skill、版本化蓝图和阶段性验证完成工作，不依赖一次性大提示词从空目录自由生成。
- 已有的任务恢复、快照、Todo、Diff、自动修复和独立完成审计必须保留，并作为新流程的基础。

### 1.5 反编译与迁移

- 用户接受反编译前的风险告知和使用协议。
- 协议是使用确认和责任告知，不是替用户取得第三方授权，也不能覆盖适用的版权、许可证或地区法律。
- 有明确源码或授权时可以完整辅助迁移。
- 只有本地闭源 JAR 时，可以进行本地分析、受控反编译和兼容层开发；反编译结果默认隔离，不自动进入导出包。
- 授权不明时至少保留 JAR 结构/API 分析和迁移评估，并限制自动生成衍生代码和重新分发。

### 1.6 插件生态

MCP 继续作为 AI 工具协议，但不能替代完整插件 SDK。插件需要扩展 UI、编辑器、语言服务、验证器、生成器、构建器、测试器、Skill 和 MCP Server。

## 3. 真实缺口与改进原则

### 3.1 真实缺口

代码审计后，当前最明确的缺口是：

1. 内容页打开文本文件时会跳到全局 `code` 视图，缺少来源上下文和返回链路。
2. Monaco 当前主要提供语言着色、主题、保存快捷键和基础编辑选项，没有项目级 LSP、语义补全、诊断、导航和重构。
3. 数据包尚未拥有与 FTB Quests/Patchouli 同等级的结构化/源码双模式领域工作台。
4. `modpackAgentPolicy` 目前更接近流程提示，`modpackPlanner` 主要解决依赖/安装规划，还没有整合包架构蓝图和质量模型。
5. `jarInspection` 和迁移服务能检查 JAR 与评估迁移，但没有完整的反编译器、符号索引和受控反编译工作区。
6. 各个编辑器有自己的保存和刷新路径，尚未形成跨 AI、Monaco、Blockbench、结构化编辑器、迁移工具和外部修改的统一变更事务层。
7. Java/Kotlin 模组开发还没有达到 IDEA 级的语言服务、调试、反编译、重构和项目索引能力。
8. MCP 已经有广泛业务工具，但还没有面向第三方代码扩展的插件运行时、权限、生命周期和 API 版本体系。

### 3.2 改进原则

- 不重做已经成熟的服务；先把现有服务接入统一项目模型和变更模型。
- 不把普通文本编辑器强行用于结构化、可视化或二进制数据。
- 不复制 IDEA 的界面；复制其在 Minecraft 开发中真正有价值的项目感知能力。
- 所有 AI 和插件写入都经过统一变更服务，不能绕过快照、Diff、冲突和审计。
- 常用能力直接可见，高级能力通过命令面板、右键菜单和上下文面板进入。
- 质量以可验证的工作流结果衡量，而不是以功能数量衡量。

## 4. 目标工作流

### 4.1 小白模式

小白用户不需要学习目录结构、JSON、Gradle 或 Loader API。界面围绕需求、进度、测试结果、修复和导出组织。可以增加更好的解释、错误摘要、修改预览和质量报告，但不把专业文件树和语言服务暴露为前置步骤。

### 4.2 专业整合包工作流

```text
选择/导入整合包
  -> 设计目标和玩家体验
  -> 选择模组、角色、端类型和蓝图
  -> 编辑配置/脚本/数据包/任务/资源
  -> 构建、启动、服务端加入和场景测试
  -> 查看 Diff、锁定清单、许可证和发布预检
  -> 导出或发布
```

### 4.3 Java/Kotlin 模组工作流

```text
创建或接管项目
  -> Gradle/Loader/Minecraft/Java 矩阵识别
  -> 代码、资源、数据和依赖统一索引
  -> Monaco 中补全、诊断、跳转、重构和调试
  -> 构建、GameTest、客户端/服务端运行
  -> 崩溃定位、AI 定向修复和回归验证
  -> JAR 检查、发布预检和发布
```

### 4.4 版本迁移工作流

```text
创建快照
  -> 选择目标版本/Loader
  -> 扫描模组、依赖、内容和源码
  -> 兼容文件/平替/源码移植/反编译分析分类
  -> 人工或 AI 做出决策
  -> 事务迁移
  -> 构建、运行、进服和内容回归验证
  -> 保留报告，失败可撤销
```

### 4.5 插件开发者工作流

```text
创建插件模板
  -> 声明贡献点和权限
  -> 本地热重载
  -> 调用受控项目/编辑器/构建/AI API
  -> 运行插件测试和兼容性检查
  -> 打包、签名、发布和升级
```

## 5. 总体架构

目标架构如下：

```text
                         ModMind Core
                              |
       +----------------------+----------------------+
       |                      |                      |
 Project Graph         Change Service          Task/Artifact Host
       |                      |                      |
       |              +-------+-------+      +-------+-------+
       |              |               |      |               |
   File Index     Monaco/Editors   Diff   Build/Test     Release
       |              |               |      |               |
       +--------------+---------------+------+---------------+
                              |
                       AI / Skill Host
                              |
                       Plugin Runtime
```

### 5.1 Project Graph

项目图是所有功能共享的事实来源，至少包含：

- 项目类型、Minecraft 版本、Loader、Loader 版本和 Java 版本。
- 模块、端类型、源码根、资源根、数据根和覆盖层。
- Gradle 配置、依赖、Mappings、源码和 JAR 来源。
- 模组身份、版本、哈希、平台、许可证和源码可用性。
- 文件类型、生成来源、只读状态、所属内容类别和关联资源。
- 任务线、数据包命名空间、注册 ID 和引用关系。
- 最近构建、测试、迁移、快照和发布状态。

### 5.2 Change Service

所有写入入口统一调用 Change Service，不允许组件直接绕过它写文件。每次变更至少记录：

- 项目路径和文件路径。
- 原始指纹、修改前内容、修改后内容。
- 来源：人工、AI、结构化编辑器、Blockbench、迁移、插件或外部文件。
- 变更原因、关联任务、时间和操作者。
- 是否需要验证、是否允许导出、是否处于冲突状态。

Change Service 负责保存、原子写入、快照、Diff、冲突和回滚。已有 `project:readFile`、`project:writeFile`、快照和 AI recovery 接口应逐步迁移到它之上。

### 5.3 文件监听与冲突

增加项目级文件监听和指纹缓存：

- 监听外部 IDE、Blockbench、脚本工具和 AI 的写入。
- 当前文档未保存时，外部写入不能静默覆盖。
- 提供保留本地、接受外部、三方合并和另存副本。
- 快照恢复、迁移和批量生成前自动冻结当前编辑状态。
- 统一处理 UTF-8、BOM、换行符、文件编码和大文件限制。

## 6. Monaco 与专业文件工作台

### 6.1 Monaco 基础升级

保留现有 `@monaco-editor/react` 和 worker 配置，但将 `MonacoCodeEditor` 升级为可复用的编辑器宿主：

- 明确区分 `modelPath`、项目路径和显示路径。
- 使用模型缓存和 `saveViewState` 保留行号、折叠、滚动位置和光标。
- 加载文件时使用请求令牌或 AbortController，防止异步读取串到另一个文件。
- 使用 `onValidate`、markers 和诊断面板展示错误。
- 支持撤销、重做、格式化、查找、替换、跳转行号、折叠和列选择。
- 支持命令面板、快捷键设置和只读模型。
- 支持 DiffEditor 审阅 AI、迁移、外部修改和快照差异。
- 让编辑器设置进入专业模式设置：字体、字号、缩进、换行、缩略图、空白字符和主题。
- 为大文件设置明确性能策略，超过编辑上限时切换到只读预览或外部工具。

### 6.2 语义能力

分层接入语言服务：

| 内容 | 第一层 | 第二层 |
|---|---|---|
| Java | JDT Language Server + Gradle classpath | Minecraft mappings、Loader API、Mixin 语义 |
| Kotlin | Kotlin Language Server | Gradle、Minecraft API 和 Kotlin 模组模板 |
| Gradle/Groovy/KTS | Monaco 语法和项目模板 | 依赖、任务、插件和版本目录感知 |
| JSON/JSON5 | JSON Schema、格式化和诊断 | Minecraft/模组/整合包专用 Schema |
| TOML/YAML/XML | Taplo、YAML Language Server、XML 语义 | 模组配置和项目约束 |
| KubeJS/JS/TS | TypeScript 语言服务 | 项目导出的模组 API、ProbeJS 类型和事件文档 |
| mcfunction | Monaco 基础语言 | Spyglass 语义服务、命令补全、目标选择器和版本诊断 |
| SNBT/NBT 片段 | 语法高亮和解析 | 类型提示、路径补全和结构化预览 |
| Markdown | marked 预览和 Monaco | 文档链接、资源引用和项目文档索引 |

推荐优先研究和集成的开源项目包括 Monaco Language Client、Spyglass、Eclipse JDT LS、Kotlin Language Server、Taplo、YAML Language Server 和 JSON Schema 表单组件。接入前必须检查许可证、打包方式和跨平台运行成本。

### 6.3 编辑器选型矩阵与开源参考

不能用 Monaco 统一承载所有内容。最终选型固定如下：

| 内容类型 | ModMind 默认编辑器 | 原因 | GitHub 参考 |
|---|---|---|---|
| Java/Kotlin/Gradle/KubeJS/文本脚本 | Monaco + LSP | 需要代码导航、诊断、补全和重构 | Monaco、monaco-languageclient、JDT LS、Kotlin Language Server |
| 数据包函数、JSON、TOML、YAML、配置 | Monaco + Schema/领域服务 | 保留源码精确度，同时获得版本和字段校验 | Spyglass、Taplo、YAML Language Server、JSON Schema |
| 配方、战利品、标签、进度 | 自研结构化编辑器 + Monaco 源码模式 | 新手和整合包作者需要结构化字段，老手需要原文控制 | JSON Forms、react-jsonschema-form 仅作为表单实现参考 |
| FTB Quests、Patchouli、键位 | 现有可视化编辑器 + 源码 Diff | 图关系、章节和冲突比纯文本更重要 | 当前自研组件和 `@xyflow/react` |
| NBT、SNBT、`level.dat`、`.mca` | 自研 React 标签树/预览器 + Monaco 片段模式 | 二进制和嵌套类型不适合纯文本 | NBTExplorer 适合作为交互参考；其 C# 桌面实现不直接嵌入 |
| 模型、贴图、动画 | Blockbench | 需要 3D、UV、骨骼和动画工作流 | Blockbench；已嵌入项目 |
| 普通图片和贴图处理 | miniPaint/图像工坊 | 需要图层、像素、透明度和处理操作 | miniPaint；已嵌入项目 |
| 任务图、流程图、关系图 | React Flow | 需要节点、边、拖拽和布局 | `@xyflow/react`；已在项目中使用 |

候选项目分为三类：

- 可直接作为依赖或服务接入：MIT/Apache 等许可证明确、浏览器或 Node 运行方式合适的项目。
- 只复用协议/数据定义：语言服务器、Schema、Minecraft 定义和解析器。
- 只作为交互参考：C# 独立桌面应用、GPL 整体应用、没有清晰许可证或只能在游戏内运行的编辑器。

特别注意：`bridge-core/editor`、Blockbench 等项目可能带有 GPL 或其他组合分发要求；在插件市场和发行包中复用前必须单独完成许可证审查。

### 6.4 文件工作台操作体验

专业文件工作台保留完整项目文件树，但改进为：

- 文件树支持搜索、过滤、最近文件和最近修改。
- 文件行显示来源、只读、生成、冲突和未保存状态。
- 文件切换时先处理未保存内容，默认保存策略可配置。
- 新建文件根据所在目录、项目类型和内容类别提供模板。
- 重命名时同步更新项目图、引用和相关资源提示。
- 删除前展示受影响引用和快照提示。
- 右键提供“上下文打开”“完整工作台打开”“在文件管理器显示”“在外部 IDE 打开”。
- 完整工作台顶部显示来源页面和返回按钮。
- 不要求多标签；使用最近文件、面包屑和快速打开替代多标签。

## 7. 内容页面的具体改造

### 7.1 数据包页面

这是第一优先级的上下文编辑对象。目前数据包内容页点击文件后会进入全局代码页面，改造为“数据包工作台”。

页面结构：

```text
数据包工作台
├── 数据包/命名空间/函数、配方、标签、战利品表、进度、世界生成
├── 内容列表和搜索
├── 当前文件标题、保存状态、验证状态、返回按钮
└── 当前文件编辑区
    ├── 概览/结构化
    └── 源码 Monaco
```

不同类型的默认体验：

- `pack.mcmeta`：元数据表单 + JSON 源码。
- `.mcfunction`：Monaco + Spyglass 命令补全、错误提示、版本提示和执行顺序说明。
- 配方：表单编辑器 + JSON 源码；提供物品 ID、标签、数量和结果预览。
- 战利品表：条件、池、函数和掉落结果结构编辑器 + JSON 源码。
- 标签：成员列表、替换策略和 JSON 源码。
- 进度：触发器、条件、奖励和 JSON 源码。
- 世界生成：Schema 表单、引用校验和原文模式。
- 命名空间入口：从注册 ID、函数调用和资源引用跳转到对应文件。

页面必须提供：

- 只打开当前内容上下文，不丢失内容列表滚动位置。
- `返回数据包` 和 `在完整文件工作台打开`。
- 文件变更后自动刷新内容清单和验证结果。
- 单文件校验、整个数据包校验和构建前校验。
- 新建函数、配方、标签、战利品表和进度模板。
- 版本相关的字段说明和错误修复建议。

### 7.2 配置与默认项

- 按 `config`、`defaultconfigs`、`serverconfig` 和模组分组。
- 对已知配置提供字段表单、默认值、类型、范围和来源说明。
- 保留 Monaco 原文模式，支持 TOML、JSON、JSON5、CFG、INI 和 properties。
- 结构化编辑和源码编辑共享同一 Change Service，切换时实时反映。
- 显示配置覆盖层：通用、客户端、服务端和最终生效值。
- 提供“恢复默认”“比较默认值”“比较上一快照”和“应用到其他模块”。

### 7.3 KubeJS 与脚本页面

- 按 `server_scripts`、`client_scripts`、`startup_scripts` 和事件类别分组。
- 脚本文件页面内直接编辑，不跳出当前内容页。
- 注册项目中模组、事件、物品、方块、配方和命令的 API 类型。
- 提供脚本语法诊断、事件文档、常见模板和安全执行边界。
- 提供脚本验证、启动阶段检查和错误日志定位到行。
- 支持只读查看脚本执行报告和最近一次运行结果。

### 7.4 服务端配置页面

- 区分服务端默认配置、运行时配置和服务端包配置。
- 提供端类型、作用域、来源和同步状态。
- 对常见配置提供表单，对未知配置使用 Monaco。
- 修改后提示是否同步到服务端包，避免客户端和服务端状态分离。
- 服务端命令、场景测试和配置验证结果可以回链到文件。

### 7.5 玩家预设与键位

当前已有结构化键位编辑和冲突检测，改进重点是：

- 原文模式在当前玩家预设页面内打开，而不是丢失页面上下文。
- 显示结构化变更与原文变更的 Diff。
- 对 `options.txt`、`optionsshaders.txt` 和其他客户端预设区分作用域。
- 对冲突键位提供一键修复建议和手动保留选项。

### 7.6 FTB Quests 与 Patchouli

这两个页面已经存在，不重做基础编辑器，重点改进协同体验：

- 可视化修改与源码文件之间显示双向 Diff。
- 写回多个文件前展示变更清单。
- 外部修改时要求重新加载或合并，禁止静默覆盖。
- 从任务节点、章节或指南页面直接跳到对应源文件并可返回。
- 保存后自动触发结构校验和相关引用检查。
- 任务书和指南书的资源、图标、链接和 ID 进入项目图。

### 7.7 资源包、光影包、界面资源和世界

- 文本类型的界面配置、FancyMenu 文件和 shader 配置支持当前页内 Monaco。
- 图片、模型、动画、音频和世界目录继续使用专用预览或专用工具。
- 资源引用显示真实预览、尺寸、格式、透明度和依赖关系。
- 世界目录显示结构、`level.dat` 状态和可选 NBT 编辑入口。
- 二进制、压缩包和不可编辑资源必须明确显示“查看/导入/使用专用工具”，不伪装成文本编辑。

### 7.8 通用文件工作台

通用工作台是高级入口，不再是所有内容编辑的必经中转站。它负责：

- 跨目录搜索和批量审阅。
- 多文件引用检查。
- AI/迁移/插件批量修改的 Diff。
- 生成文件、源码文件和只读依赖的统一浏览。
- 复杂跨目录重构和项目级操作。

## 8. Java/Kotlin Minecraft IDE 能力

### 8.1 项目导入和 classpath

- 解析 Gradle Wrapper、Gradle 版本、插件、Source Set 和依赖。
- 管理 Minecraft、Loader、Mappings、Java 和 Kotlin 版本矩阵。
- 使用 Gradle Tooling API 或等价服务生成可靠 classpath。
- 监听 `build.gradle`、`gradle.properties`、版本目录和依赖变化。
- 为语言服务器提供源码 JAR、映射和依赖源码。
- 使用缓存避免每次打开项目都完整解析。

### 8.2 编辑、导航和重构

第一阶段必须覆盖：

- 类、方法、字段、构造器、参数和资源引用跳转。
- 查找引用、文件符号、项目符号和实现关系。
- 自动导包、补全、悬浮信息和错误诊断。
- 格式化、代码操作、重命名和安全删除。
- Mixin 目标、EntryPoint、注册 ID、资源路径和数据生成引用的 Minecraft 专用索引。

后续覆盖：

- 跨 Java/Kotlin/资源的重构。
- Loader 转换辅助。
- 版本映射迁移提示。
- API 变更替换建议。

### 8.3 构建、运行和调试

- 一键选择客户端、服务端、数据生成、GameTest 和发布任务。
- 将 Gradle 输出、编译错误、崩溃堆栈映射到源码行。
- 支持 JDWP 调试：断点、条件断点、调用栈、变量、监视表达式和异常暂停。
- 支持运行配置保存、复制和按项目版本隔离。
- 将游戏日志、服务端日志、崩溃报告和最近修改文件关联。
- 支持构建失败后 AI 定向分析，而不是重新扫描全部项目。

### 8.4 反编译和 API 浏览

- 依赖 JAR 可只读查看类、包、方法签名、注解和资源。
- 优先使用官方源码、Mappings 和公开源码归档。
- 对受控本地反编译结果标记来源、时间、哈希和只读状态。
- 反编译结果不得默认进入项目源码或发布归档。
- 对闭源模组提供 API/符号浏览、兼容层模板和调用建议。

### 8.5 IDEA/VS Code 兼容策略

用户认为 IDEA 好用，核心通常不是喜欢它的窗口布局，而是它替用户完成了大量判断：准确补全、实时错误反馈、类和引用跳转、自动导包、重命名、安全重构、项目依赖感知、Gradle 运行、调试和稳定的错误定位。ModMind 必须按这些结果验收，而不是只验收编辑器是否能输入代码。

ModMind 不复制 IDEA 的通用企业 Java 插件生态，而是提供更懂 Minecraft 的垂直能力。最终替代范围包括 Minecraft 开发必需的编辑、构建、运行、调试、性能分析、迁移和扩展能力；普通企业 Java、Android、Spring 等非 Minecraft 工作流不属于产品目标。

外部 IDE 入口在达成以下条件前保留：

- Java/Kotlin 常用编辑任务稳定。
- 构建、运行、调试和测试完整。
- 依赖和源码跳转可靠。
- 常见 Minecraft Loader 工作流覆盖。
- 崩溃定位和重构不会明显丢失信息。

达到这些条件后，IDEA/VS Code 入口可以从主工具栏移到“外部工具”菜单，但不强制删除。删除外部入口需要真实使用数据证明用户不再依赖它，而不是仅凭功能清单判断。

## 9. 整合包架构 Skill 与半成品蓝图

### 9.1 Skill 与蓝图的职责

`modpack-architect` Skill 负责决策，蓝图负责可复用结构，验证器负责证据。

Skill 不应只告诉 AI“参考成熟整合包”，而应指导 AI：

- 识别目标玩家、游玩时长、题材和难度。
- 定义模组角色、依赖、端类型和性能预算。
- 设计阶段性 progression、任务和引导。
- 选择配置基线、覆盖层和资源策略。
- 规划测试场景、服务端加入和发布检查。
- 遇到不兼容模组时选择替代、迁移、兼容层或降级目标。

### 9.2 蓝图模型

蓝图是版本化、可验证、可组合的半成品，不是一次性提示词。建议包含：

- Minecraft/Loader/Java 版本矩阵。
- 题材、目标玩家和预计游玩时长。
- 模组角色与依赖图。
- 初始模组清单和可替换候选。
- 配置基线和端类型覆盖。
- 任务章节和阶段目标。
- 数据包、脚本、资源和指南书入口。
- 性能预算、内存建议和测试场景。
- 已知风险、许可证和来源信息。

首批蓝图覆盖：科技、冒险、魔法、原版增强、建造、生存、多人服务器和轻量整合包。蓝图应允许替换版本、Loader 和关键模组，并自动重新计算依赖、内容和测试计划。

### 9.3 AI 分阶段生成

```text
需求提取
  -> 项目扫描
  -> 蓝图/模组方案
  -> 用户目标确认或高级模式自动执行
  -> 骨架和依赖
  -> 配置与内容
  -> 任务/脚本/资源
  -> 构建和运行验证
  -> 定向修复
  -> 导出和发布预检
```

每阶段都记录：预计文件数、预计构建次数、风险、耗时和 AI 使用量。失败时只重新执行相关阶段。

### 9.4 质量模型

质量报告至少包含：

- 依赖和版本一致性。
- 客户端/服务端/通用内容一致性。
- 启动、构建和服务端加入结果。
- 关键任务和脚本场景结果。
- 资源引用、数据包结构和配置合法性。
- 内存、启动时间和明显性能风险。
- 内容重复、空壳文件和未完成占位内容。
- 许可证、来源和发布清单。

当前已有构建、预检、HeadlessMC、服务端验证、测试矩阵、AI 审计和快照，应直接接入这套质量报告，而不是另起一套重复系统。

### 9.5 成本控制

- 缓存项目分析、模组身份、依赖和版本数据。
- 复用蓝图和已验证配置，不让 AI 重写已有正确文件。
- 先执行低成本静态校验，再决定是否构建或启动游戏。
- 自动修复使用明确轮次、错误指纹和停止条件。
- 高成本任务显示预计修改文件、构建次数和可能的运行测试。
- 对重复失败提供“需要人工决策”状态，而不是无限重试。

## 10. 模组迁移、JAR 分析与受控反编译

### 10.1 已有能力的延伸

当前 JAR 检查和整合包迁移服务已经提供哈希、Loader、类数量、依赖、候选版本、平替和手动 JAR 入口。新能力应建立在这些证据上，不重做身份识别和迁移事务。

### 10.2 迁移分类

| 类型 | 处理方式 |
|---|---|
| 目标版本有官方文件 | 直接选择、锁定哈希并验证依赖 |
| 有官方平替 | 人工/AI 选择，记录功能差异和风险 |
| 有公开源码 | 创建目标版本移植模块，保留源码来源和许可证 |
| 用户拥有授权的闭源 JAR | 本地受控反编译、API 分析、兼容层或移植辅助 |
| 授权不明的闭源 JAR | 结构/API 分析和迁移评估；限制自动衍生代码与分发 |
| 无法解析或高度混淆 | 保留未知状态、提供手动决策和替代方案 |

### 10.3 反编译工作区

需要新建独立的本地分析工作区：

- 用户明确选择本地 JAR。
- 首次进入显示协议和风险说明。
- 记录 JAR 哈希、来源、时间、用户确认和目标项目。
- 反编译结果存放在项目工具目录或用户缓存，不进入普通源码树。
- 默认只读，显示“反编译结果，不是项目源码”。
- 支持类、方法、字段、注解、资源和依赖浏览。
- 支持导出 API 摘要，而不是默认导出完整衍生源码。
- 兼容层代码必须由用户明确创建到项目中，并附带来源说明。
- 发布预检检测是否误把受控反编译结果打包。

### 10.4 技术路线

先实现 JAR 结构、符号、字节码和 API 检查；之后按许可证和跨平台条件选择 CFR、FernFlower、Procyon 或其他方案。所有依赖必须进入第三方声明和分发审查。

### 10.5 迁移验证

迁移不能以“生成了源码”作为成功。必须继续执行：

- 编译和资源检查。
- Loader/映射目标检查。
- 客户端启动。
- 服务端启动和进服。
- 关键功能场景。
- 迁移前后行为差异报告。
- 失败时保留快照并支持撤销。

## 11. 插件平台设计

### 11.1 插件清单

建议使用 `.modmind-plugin/plugin.json`，至少声明：

- 插件 ID、名称、版本、作者和许可证。
- ModMind API 版本和兼容范围。
- 入口文件和 UI 资源。
- 贡献点。
- 所需权限。
- 附带 Skill、Schema、语言服务和 MCP Server。

### 11.2 贡献点

首批贡献点：

- `commands`：命令面板和快捷键。
- `views`/`panels`：侧边栏、工作区和属性面板。
- `editors`：文件类型编辑器和结构化编辑器。
- `languages`：Monaco 语言定义、LSP 和诊断。
- `schemas`：JSON/TOML/YAML/自定义格式校验。
- `generators`：内容生成器和模板。
- `blueprints`：整合包半成品蓝图。
- `validators`：构建前、导出前和运行时检查。
- `tasks`：构建、测试、迁移和发布任务。
- `aiSkills`：Skill、提示模板和领域决策器。
- `mcpServers`：对 AI 提供插件能力。
- `projectTemplates`：项目和模块模板。

### 11.3 插件 API

插件必须通过受控 API 访问项目：

- `workspace.projects`
- `workspace.fs`
- `workspace.changes`
- `workspace.index`
- `editor.models`
- `editor.diagnostics`
- `commands`
- `window`
- `tasks`
- `build`
- `tests`
- `ai`
- `mcp`
- `storage`

插件不得直接修改项目文件、直接访问 Electron 主进程或绕过 Change Service。

### 11.4 安全和权限

权限分为文件、网络、外部进程、AI、系统命令、发布凭证和项目写入。默认最小权限，首次安装显示权限用途。插件运行在独立进程或受控 Worker 中，异常不能拖垮主窗口。

### 11.5 生态分期

第一阶段：TypeScript/JavaScript 本地插件、官方插件和开发者模式热重载。

第二阶段：插件打包、API 兼容检查、签名、权限审查、自动更新和跨平台分发。

第三阶段：插件市场、版本评分、依赖关系、沙箱强化、回滚和社区 Skill/蓝图生态。

MCP 可以作为插件的一个贡献点，而不是插件系统本身。

## 12. 分期开发路线

### 阶段 0：基线、契约和回归保护

目标：不破坏现有能力，建立统一接口。

工作项：

- 盘点现有 IPC、主进程服务和页面入口。
- 定义 Project Graph、Change Service、Editor Context、Diagnostic、Task 和 Plugin API 类型。
- 为现有 AI recovery、快照、Git、迁移、构建和测试补充端到端回归。
- 记录当前功能矩阵，区分已实现、部分实现和待建设。
- 清理启动检查和单实例测试路径，建立稳定的 Playwright Electron 检查方式。

退出标准：现有整合包、模组、迁移、构建、测试、发布和恢复流程有可执行回归证据。

### 阶段 1：上下文编辑和文件变更基础

目标：解决“内容页跳到通用编辑器且回不来”的核心问题。

工作项：

- 新增编辑上下文对象，记录来源 View、内容类别、路径和返回位置。
- 把数据包、配置、脚本、服务端、界面和玩家预设接入上下文编辑器。
- 统一保存、返回、未保存确认、刷新和错误提示。
- 实现文件指纹、外部修改检测和基本冲突提示。
- 改进 Monaco 模型生命周期、加载竞态、撤销和视图状态。
- 增加 AI/迁移/结构化编辑器使用的 Diff 入口。

退出标准：用户可以在当前内容页打开、编辑、保存、返回、切换文件和处理外部修改，且不会丢失页面上下文。

### 阶段 2：数据包与专业内容编辑

目标：让数据包和常见配置不再只是通用文本。

工作项：

- 数据包工作台和命名空间/类型树。
- `.mcfunction` 语义服务和版本诊断。
- 配方、战利品、标签、进度和 `pack.mcmeta` 双模式编辑。
- 配置 Schema、表单/源码切换和覆盖层。
- KubeJS API 类型、事件模板和启动错误定位。
- FTB/Patchouli/键位与源码 Diff 和返回链路。
- NBT/SNBT 结构化编辑器原型。

退出标准：常见整合包文本内容可以在领域页面内完成创建、修改、验证和回退。

### 阶段 3：项目级语义编辑和 Java/Kotlin IDE 基础

目标：替代日常 IDEA/VS Code 编辑工作。

工作项：

- Gradle classpath、Source Set、依赖源码和 mappings 索引。
- JDT LS、Kotlin Language Server 和 Monaco Language Client 接入。
- 项目符号、引用、补全、诊断、格式化、自动导包和代码操作。
- Minecraft Loader、Mixin、EntryPoint、注册表和资源引用索引。
- 项目级搜索、快速打开、命令面板和快捷键。
- AI 选区解释、补丁生成和 Diff 应用。

退出标准：常见 Java/Kotlin 模组功能可以在 ModMind 内完成编辑、导航、诊断和小范围重构。

### 阶段 4：构建、调试和运行 IDE

目标：替代 IDEA/VS Code 的运行和调试工作流。

工作项：

- 运行配置、Gradle 任务和环境矩阵。
- JDWP 调试器、断点、调用栈、变量和监视。
- 崩溃堆栈/日志到源码行映射。
- GameTest、HeadlessMC、客户端和服务端调试入口。
- JAR/API 浏览、源码优先和受控反编译工作区。
- 性能采样、启动时间、内存和基础 JFR 报告。

退出标准：用户可以在 ModMind 内完成构建、运行、调试、测试和崩溃定位。

### 阶段 5：整合包架构 Skill 和蓝图

目标：减少整合包生成时间、费用和低质量空壳内容。

工作项：

- `modpack-architect` Skill。
- 多题材版本化蓝图。
- 模组角色、依赖、端类型和性能预算模型。
- 分阶段生成和成本预估。
- 内容完整度、任务线、启动、进服、性能和发布质量报告。
- 失败阶段重试、缓存和人工决策节点。
- 对成熟整合包经验提炼为原则、公开元数据和可验证模板，不复制受保护内容。

退出标准：AI 可以从蓝图生成可验证半成品，并在有限轮次内完成定向补齐，而不是从空目录无限生成。

### 阶段 6：受控迁移和反编译

目标：支持目标版本缺少模组时的深度迁移辅助。

工作项：

- JAR 分析和符号索引。
- 用户协议、授权状态和来源记录。
- 本地隔离反编译工作区。
- API 摘要、兼容层模板、源码移植和映射辅助。
- 迁移前后 Diff、构建、运行、进服和功能验证。
- 反编译结果防误打包和发布预检。

退出标准：迁移任务可以明确区分官方兼容、平替、源码移植、授权闭源分析、未知和阻塞状态，并能安全撤销。

### 阶段 7：插件 SDK 和生态

目标：让 ModMind 能持续吸收第三方 Minecraft 工具和社区能力。

工作项：

- `.modmind-plugin/plugin.json` 和插件宿主。
- 命令、页面、编辑器、语言服务、Schema、生成器、验证器、任务和 Skill 贡献点。
- 权限、沙箱、独立进程、日志和 API 版本。
- 本地开发、热重载、兼容检查和测试工具。
- 官方插件迁移和 MCP 适配器。
- 签名、审核、市场、更新、回滚和许可证展示。

退出标准：第三方可以在不修改 ModMind 核心代码的情况下增加一种内容格式、一个语言服务或一个构建/测试适配器。

## 13. 测试与验收

### 13.1 文件与编辑器测试

- 文件加载竞态不会串文档。
- 切换文件、返回页面和项目切换不会丢失未保存内容。
- 外部修改能被检测并进入冲突处理。
- UTF-8、BOM、换行和大文件边界正确。
- Monaco、结构化编辑器和 Blockbench 共享保存状态。
- AI/迁移/插件 Diff 可以审阅、应用、拒绝和恢复。

### 13.2 数据包与内容测试

- 正确识别数据包内容类型和命名空间。
- `.mcfunction`、配方、战利品、标签、进度和世界生成校验正确。
- 结构化模式和原文模式互相转换不丢字段。
- 当前页面编辑后内容列表和验证结果自动刷新。
- 版本差异产生明确诊断而不是静默接受。

### 13.3 Java/Kotlin IDE 测试

- Gradle classpath 与语言服务器初始化。
- 依赖源码、Mappings、类和方法跳转。
- 补全、诊断、自动导包和重构。
- Fabric/Quilt/Forge/NeoForge 模板。
- 客户端、服务端、GameTest 和调试运行配置。
- 编译错误、Mixin 错误和崩溃堆栈定位。

### 13.4 AI 与整合包测试

- 同一需求重复执行的文件变更范围稳定。
- 蓝图适配不同版本、Loader 和模组替代。
- AI 阶段失败后只重试相关阶段。
- 预算、轮次和停止条件有效。
- 构建、启动、进服、任务和发布证据完整。
- recovery、快照、恢复前现场和撤销路径完整。

### 13.5 迁移与反编译测试

- JAR 哈希、来源、授权确认和隔离目录正确。
- 反编译结果不会出现在默认项目导出中。
- 迁移失败可以恢复到迁移前状态。
- 官方版本、平替、源码移植、闭源分析和未知状态不会混淆。
- 目标版本缺少模组时能产生可执行的人工待办。

### 13.6 插件测试

- 无权限插件不能写项目、启动进程或访问网络。
- 插件崩溃不会拖垮主应用。
- API 版本不兼容时阻止加载并显示修复建议。
- 插件对项目的写入全部出现在 Diff、快照和审计中。
- 禁用、卸载、回滚插件后项目仍可打开。

## 15. 风险与边界

### 15.1 范围风险

“完全替代 IDEA”是长期产品目标，不能作为第一期承诺。第一期应先覆盖整合包和常见 Minecraft 模组开发闭环，再逐步补足调试、性能分析和插件生态。

### 15.2 语言服务成本

Java/Kotlin LSP、Gradle classpath、Mappings 和 Minecraft 语义索引是高复杂度系统，需要独立缓存、进程管理和版本兼容测试。不能只把 Monaco 语言名称从 `plaintext` 改成 `java` 就宣称有 IDEA 能力。

### 15.3 反编译与许可证

协议不能替代授权。必须保留来源、哈希、授权状态、隔离目录和发布阻断规则。具体许可证和地区合规应在发布前由专业人员审查。

### 15.4 插件安全

第三方插件可以运行任意代码、访问网络或修改项目，因此权限、沙箱、签名、更新和回滚不是可选项。市场应晚于本地 SDK 和权限模型。

### 15.5 性能

整合包和模组项目可能包含大量 JAR、源码和资源。项目图、语言服务、文件监听、Monaco 模型和资源预览都必须使用增量索引和缓存，不能在每次页面切换时全量扫描。

### 15.6 外部工具兼容

在 ModMind 达到稳定覆盖率前，不应删除 VS Code/IDEA 入口。可以把它们移到“外部工具”菜单，记录用户离开的原因，用数据指导后续补齐。

## 16. 交付优先级结论

第一优先级不是新增更多页面，而是：

```text
统一文件变更基础
  -> 上下文内编辑
  -> 数据包/配置/KubeJS 领域编辑
  -> Java/Kotlin 项目索引和语义编辑
  -> 调试与迁移
  -> 整合包 AI 蓝图
  -> 插件生态
```

原因是所有后续能力都依赖同一套项目模型、文件变更、Diff、诊断、任务和验证机制。如果先分别实现插件、反编译、蓝图和更多页面，最终会继续出现互相覆盖、状态不同步和入口分散的问题。

最终完成标准不是“功能列表全部打勾”，而是以下工作流在 ModMind 内闭环：

- 新手可以不理解源码完成整合包制作、测试和导出。
- 专业整合包作者可以不离开内容页完成配置、数据包、脚本、任务和资源维护。
- Java/Kotlin 模组作者可以不打开 IDEA 完成编辑、构建、调试和测试。
- 迁移开发者可以完成目标版本分析、源码/授权 JAR 迁移和回归验证。
- 第三方开发者可以通过插件 SDK 增加新的 Minecraft 能力，而不修改核心代码。

## 17. 已决定的实施参数

本节替代“待确认项”。后续实现按以下默认决策推进，除非新的产品事实证明必须调整。

### 17.1 版本与 Loader 范围

- 第一优先级是 Java Edition 的 Fabric、Quilt、Forge 和 NeoForge。
- 版本能力不写死为单个 Minecraft 版本，跟随现有 Loader Catalog 和项目模板维护；每个版本显示稳定、实验或不支持状态。
- 首批语言服务必须覆盖当前模板实际能创建和构建的版本；新版本先进入实验状态，完成构建/启动/导航回归后再标记稳定。
- Bedrock/网易项目保留现有内容、构建和导出能力，Project Graph/Change Service 的第一版先以 Java 项目和整合包为完整目标，随后扩展其他平台。

### 17.2 调试和性能分析

- IDE 目标必须包含客户端、服务端和 GameTest 调试，不把调试器限定为后续可选功能。
- 第一批调试能力覆盖断点、条件断点、调用栈、变量、监视、异常暂停、日志联动和运行配置。
- 性能能力覆盖启动时间、内存、线程和基础 JFR/采样报告；更复杂的 Profiler 以插件贡献点开放，但核心必须能查看和关联基本结果。
- 调试、性能和崩溃定位全部进入项目任务、证据和恢复流程。

### 17.3 反编译实现

- 第一版先交付 JAR 结构/API 浏览、符号索引、Mappings 和源码优先策略。
- 反编译器采用可替换 Provider，不把许可证不清晰的实现硬编码进核心。
- 只有完成许可证和跨平台分发审查的 Provider 才能随发行包提供；其他 Provider 作为用户本地安装或插件。
- 反编译结果默认只读、隔离、带哈希和来源元数据，并被发布预检阻断。

### 17.4 插件 SDK 与市场

- 第一阶段只支持本地 TypeScript/JavaScript 插件、官方插件和开发者模式热重载。
- 插件必须使用 `.modmind-plugin/plugin.json`、权限声明和版本化 API。
- 插件不能绕过 Change Service，不能直接获得 Electron 主进程权限。
- 本地 SDK、权限、进程隔离和兼容测试稳定后，再做签名、审核、自动更新和市场。
- 市场不是插件接口的前置条件；核心必须先做到第三方可以在本地开发和验证插件。

### 17.5 外部 IDE 策略

- 目标是 Minecraft 开发工作流不需要 IDEA/VS Code，而不是一开始删除它们。
- 在 Java/Kotlin 编辑、构建、调试、性能分析、迁移和发布达到验收标准前，保留外部 IDE 应急入口。
- 达标后移到“外部工具”菜单，并保留项目目录、源码和运行配置的开放性。

### 17.6 AI 与小白模式

- 小白模式界面可以改进，但仍保持“需求、进度、测试、修复、导出”的低认知负担。
- 小白模式背后的 AI 规划、蓝图、缓存、质量验证、成本控制和恢复流程可以升级。
- 专业模式显示完整计划、文件 Diff、诊断、任务证据和高级控制。
- 整合包蓝图覆盖科技、冒险、魔法、原版增强、建造、生存、多人服务器和轻量整合包，不为单一题材设计架构。

### 17.7 完成定义

“完全不需要 IDEA”按 Minecraft 领域能力定义，必须最终覆盖：

- Java/Kotlin 编辑、语义补全、诊断、跳转、引用、自动导包和重构。
- Gradle、依赖、Mappings、Loader、Mixin、EntryPoint 和资源索引。
- 客户端、服务端、GameTest 的运行、调试、日志和崩溃定位。
- 基础性能采样、内存和启动分析。
- JAR/API 浏览、授权反编译和版本迁移。
- 整合包内容、任务、配置、脚本、资源、服务端和发布闭环。
- 插件、Skill、语言服务、Schema、验证器、生成器和 MCP 扩展。

普通企业 Java IDE 能力不纳入完成定义，但 Minecraft 开发中真实需要的 IDEA 级能力纳入完成定义。

### Todo 使用规则

- P0 任务未完成前，不应把依赖它的后续功能标记为稳定。
- 每个 Todo 完成时必须补充代码、测试、用户入口和验收证据；“写了接口”不等于完成。
- 一个 Todo 如果跨越多个主进程服务或页面，应拆成实现、集成和回归三个 Issue。
- 任何 AI、插件、反编译或迁移任务都必须经过 Change Service、Diff、快照和发布边界检查。
- 阶段退出标准优先于日历时间；如果构建、运行、调试或回滚证据不足，阶段保持进行中。
