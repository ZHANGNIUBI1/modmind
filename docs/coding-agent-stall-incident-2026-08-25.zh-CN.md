# Coding Agent 静默超时与任务悬挂事故分析

**日期：** 2026-08-25  
**应用版本：** 1.3.11  
**证据来源：** `log/ModMind-diagnostics-2026-08-25T02-26-51-527Z.zip`  
**分析范围：** 仅依据诊断包，不包含源码检查或本地复现。

## 结论

用户任务并非卡在 Gradle 编译。实现文件已经生成，托管构建最终成功，但 Coding Agent 多次进入 120 秒无输出窗口，被宿主连续恢复；最后一次工具输出后，会话没有终态事件，任务状态也没有同步到实际进度，最终表现为界面持续进行中。

当前证据支持将问题归类为 **Agent 静默检测、恢复流程和任务状态持久化之间的生命周期异常**。日志不足以确认单一代码根因，不能直接断言是 CLI、事件解析器或监听器泄漏中的某一处独立造成。

## 用户影响

- 用户看到任务长期停留在“检查工程结构”。
- 实际实现和构建已发生，但界面未反映，用户无法判断是否可以结束任务。
- 自动验证和隔离 Minecraft 启动测试没有完成。
- 同一会话被反复恢复，产生额外等待和计算消耗。

## 日志证据

### 1. 静默超时重复发生

`app-logs/ai-attempt-audit.jsonl` 对同一会话 `coding-1787620093401` 记录了 7 次：

```text
Codex 在 120 秒内没有收到任何输出
```

这些记录均以 `retry` 结束，没有正常的任务终态。

### 2. 构建实际成功

`project/builds/minecraft-test-build.log` 显示：

```text
BUILD SUCCESSFUL in 1s
5 actionable tasks: 5 up-to-date
```

Agent 输出还显示多个实现类已经生成。因此不能把本次悬挂归因于编译错误或 Gradle daemon 退出。

### 3. 持久化状态与实际执行不一致

`project/ai/active-ai-task.json` 在导出时仍包含：

```text
changedFiles: []
applyRounds: 0
inspect: in_progress
implement/validate/runtime: pending
```

同一文件同时记录 `lastBuildSucceeded: true`、`buildCount: 5`，并把工作流 `build` 标为完成。实现产物、构建状态和 Todo 状态互相矛盾。

### 4. 应用资源不是限制因素

导出时系统仍有约 21.8 GB 可用内存和 194 GB 可用磁盘。应用其他周期 IPC 正常完成，没有进程级崩溃证据。

## 其他潜在问题

### P1：AbortSignal 监听器可能未在重试后清理

日志多次出现：

```text
MaxListenersExceededWarning: 11 abort listeners added to [AbortSignal]
```

该警告与频繁重试处于同一任务周期，说明取消/超时监听器可能跨 attempt 累积。它可能放大后续不稳定性，但当前日志不能证明它就是静默悬挂的直接原因。

### P1：任务进度写入缺少一致性保证

构建成功后，文件变更、Todo 和工作流证据没有原子或幂等地汇总。恢复会话时如果只读取旧的 active task，界面会长期显示过期阶段。

### P2：Agent 工具调用存在协议参数错误

日志包含多次缺少 `cell_id`、`timeout_ms` 小于最小值等工具路由错误。这些错误可恢复，但会增加静默窗口并浪费 attempt。

### P2：托管 JDK 环境注入不稳定

Agent 早期命令一度找不到 `JAVA_HOME` 和 `jar`，随后改用 ModMind 托管 JDK 才完成构建。所有由 Agent 启动的构建和诊断命令应继承同一套 JDK 环境。

### P3：外部服务与输入限制问题

- 远程审查不可用时已降级到本地规则，未阻断本任务。
- 日志出现接入 Key 失效、模型列表读取失败和远程控制未启用。
- 一个 ModernUI JAR 因超出 20 MB 附件限制被拒绝。

这些问题需要独立处理，但没有证据表明它们导致本次最终悬挂。

## 修复建议

### P0：收敛 Agent attempt 生命周期

1. 为每个 attempt 维护唯一的静默计时器和 AbortController，并在输出、结束、重试或异常路径统一释放。
2. 区分“CLI 仍运行但无模型输出”和“子进程已经失联”；工具运行中应使用独立心跳，不应只依赖文本输出。
3. 恢复前明确关闭或接管旧 attempt，禁止同一 run 同时存在两个活跃消费者。
4. 设定总重试上限和总时长；超过阈值后进入可见失败态，并保留“继续任务”操作，避免无限悬挂。
5. 将 terminal event 作为一次且仅一次的状态迁移，重复事件必须幂等。

### P0：统一任务实际状态与界面状态

1. 每次文件变更、构建、验证和运行测试完成后立即写入 task checkpoint。
2. 恢复时以磁盘变更和已保存证据校正 Todo，不盲信旧的 `in_progress`。
3. 构建成功不能代表任务完成；缺少 `validate` 或 `runtime_test` 时应明确显示剩余步骤。
4. 若 Agent 进程结束但没有终态事件，宿主应生成 `interrupted` 或 `failed` 终态，不能永久保留 `running`。

### P1：修复和观测监听器泄漏

不要仅通过提高 `MaxListeners` 隐藏警告。应记录每个 run/attempt 的监听器注册和清理次数，并在开发环境断言二者相等。

### P1：固定托管执行环境

Codex 启动、Gradle 构建和 Agent 内部 shell 命令统一注入托管 JDK 的 `JAVA_HOME` 与 `PATH`，并在任务开头记录一次有效环境摘要。

## 验收标准

- 连续制造 3 次 120 秒静默后，每次旧 attempt 的计时器和 abort listener 均被清理，进程监听器数量不增长。
- 工具执行超过 120 秒但持续报告心跳时，不触发错误重试。
- 恢复后同一 run 只有一个活跃 attempt，旧 attempt 的迟到输出不会改变新状态。
- 文件已修改且构建成功时，`changedFiles`、`applyRounds`、Todo 和 workflow evidence 与实际一致。
- Agent 无终态退出时，界面在限定时间内进入 `interrupted/failed`，并提供可恢复入口。
- 完成事件重复到达不会重复构建、重复写状态或重复向用户展示完成消息。
- 托管构建环境中 `java`、`jar` 和 `JAVA_HOME` 从任务开始即有效。

## 建议回归测试

- attempt 静默超时与监听器清理单元测试。
- 子进程仍运行、长工具调用、无文本输出场景的集成测试。
- terminal event 缺失、重复和乱序场景的状态机测试。
- 恢复会话后 checkpoint 重放和 Todo 校正测试。
- 托管 JDK 环境继承测试。
- 诊断导出中增加 attempt 状态、最后心跳、监听器数量和终态原因字段的快照测试。

## 非本次根因

根据现有日志，下列因素可以暂时排除为主要原因：Gradle 编译失败、系统内存不足、磁盘空间不足、Electron 主进程整体冻结。Minecraft 26.2 在导出时仍处于下载阶段，但悬挂在下载开始前已经出现，不能解释此前 7 次 Agent 静默超时。
